# 范围界定——定义结果、边界与责任

**目标：** 把一个已验证的问题变成一份可执行、可验收的一期合同：谁在用、改变什么、改多少、明确不做什么、谁负责什么，以及何时停止。范围模糊是绝大多数 AI 交付失败的根因。

> 上游输入：`01-discovery.md` 的问题陈述与基线。下游输出：`03-integration-architecture.md` 的设计输入。

## 输入与输出

| | |
|---|---|
| 输入 | `01-discovery` 的问题陈述、量化基线、相关者地图 |
| 输出 | `SCP-<client>-vN` 范围合同（冻结后变更必须回到本文件）；三维机会评估记录 |
| 下游 | `03-integration-architecture.md`、`04-evaluation.md` 的验收口径 |

## 第 1 步：三维评估机会 <!--a:step1-->

在签任何合同前，先确认这个机会*值得*被合同化。每个候选机会三维各打 1–5 分；**用乘法不用加法**——任一维为 0 即否决。

| 维度 | 要回答的问题 |
|---|---|
| **业务价值** | 基线够大吗？高管把它排进前五吗？触及收入、风险或合规吗？ |
| **技术可行性** | 数据现在可得且够干净吗？最小链路 1–2 周内能端到端打通吗？ |
| **责任风险** | 有具名 Owner 吗？AI 出错谁担责？动作可回滚吗？ |

| 决策 | 条件 |
|---|---|
| **优先做** | 价值高、可行、Owner 已具名 |
| **补齐再做** | 价值在但数据/Owner/条件缺失 |
| **暂不推进** | 价值过小、条件不成立或风险无人接受 |

## 第 2 步：点名第一用户与真实入口 <!--a:step2-->

系统必须落在工作已经发生的地方——而非一个用户永远不会打开的新后台。用一句话写清**第一用户**与**现有入口**。

```text
First user:   <who actually does the task>   第一用户：<真正做这件事的人>
Entry point:  <the IM / dashboard / system they already use>   现有入口：<他们已经在用的 IM/看板/系统>
```

## 第 3 步：写出业务结果（基线 → 目标） <!--a:step3-->

用对 `01-discovery` 基线的可测增量替换"提升效率"。

```text
Before: <baseline number from discovery>   改造前：<发现阶段的基线数字>
Target: <measurable after-state>            目标：<可度量的改造后状态>
Proof:  <how the after-state will be observed, not asserted>   证据：<观察而非声明的验证方式>
```

目标测不出来，就不是结果，只是愿望。

## 第 4 步：画出边界与围栏动作 <!--a:step4-->

| 边界 | 含义 | 示例 |
|---|---|---|
| **要做（本轮）** | 本期必须交付什么 | "在飞书回答课程事实问题" |
| **暂不做** | 真实但延期，不在本期 | "图片回复、其他课程" |
| **绝不自动承诺** | 系统不得单独决定 | "价格、退款、权益、授权" |
| **围栏动作** | 回写/排产/采购/对外承诺——未重新授权一律禁止 | "禁止回写 ERP、禁止采购动作、禁止对客户承诺（仅人工）" |

"绝不自动承诺"项按设计交给真人，而非按异常处理。

## 第 5 步：分配责任与风险 <!--a:step5-->

| 角色 | 责任 |
|---|---|
| 业务/知识责任人 | 保持源头事实当前且正确 |
| 工程/系统责任人 | 运行系统、修复故障 |
| 一线管理者/用户 | 使用、标记错误或越界回答 |
| 决策/发起人 | 批准范围扩张与残余风险 |

一个任务可有多个 R/A/C/I——但 **Accountable（最终负责）** 必须始终无歧义。范围合同还须写明：**业务 Owner**（担结果，具名）、**技术 Owner**（担运行，具名）、**风险接受人**（谁接受残余风险）、**停止条件**（数值触发线）、**升级路径**（通知谁、SLA 多长）。"IT 牵头，业务那边知道这事"不是担责。

## 第 6 步：定义验收口径 <!--a:step6-->

| 验收轴 | 问题 |
|---|---|
| 输入 | 哪些真实问题/数据算作测试集 |
| 输出 | 正确答案必须包含什么 |
| 边界 | 什么必须触发转人工、绝不自动承诺 |
| 用户 | 哪些真实用户验收（而非开发者自己） |

## 第 7 步：锁定停止、收窄与回退条件 <!--a:step7-->

提前决定何时停止、收窄或回退——这样日后才能无争执地停下来。

```text
Stop if:   <value not confirmed / data not obtainable / risk not acceptable>
Narrow if: <a key assumption fails but direction still holds>
Revert if: <the problem itself is gone or reshaped>
```

## 第 8 步：切出最小端到端闭环 <!--a:step8-->

范围可以窄，但必须跑通一条从入口到结果的真实链路——而非一堆横向并排的演示。

```text
First user:   <only these participants>     第一用户：<仅这些参与者>
Entry point:  <only this existing workflow position>   入口：<仅这一个既有工作位>
Data:         <only these sources>          数据：<仅这些来源>
Actions:      <only these permitted moves>  动作：<仅这些允许的动作>
Cycle:        <how long it runs to earn a verdict>   周期：<跑多久能给出判断>
```

## 第 9 步：把 ROI 当成假设来定价 <!--a:step9-->

预期收益是待验证的主张，不是已经落袋的收益。

| 一侧 | 内容 |
|---|---|
| 预期收益 | 基线→目标的差值，并估值 |
| 完整成本 | 建设 + 运行 + 迁移/变更成本 |
| 结论 | 值得投入 / 调整范围 / 不启动 |

## 第 10 步：冻结范围合同 <!--a:step10-->

把前九步落到 `SCP-<client>-vN`（字段见 `templates/scope-contract.md`）：结果边界、范围边界（含明确不做清单）、责任边界、待 PoC 检验的开放假设。业务与技术 Owner 签字。**冻结后出现新事实，回到本文件重开并说明变更，禁止静默扩大。**

## 模板 / 工件 <!--a:template-->

- `templates/scope-contract.md` —— 范围合同（结果/范围/责任三类边界）
- 产出 ID：`SCP-<client>-vN`

**门禁提示：** 三份开放假设必须在 `04-evaluation.md` 被显式证伪或证实；未做三维评估就签合同、或验收口径仍由开发者掌握，都不得视为范围已冻结。

<correct_patterns>

### 好的结果 + 闭环

```text
Before:  sales wait 2–4 h per technical question (discovery baseline)
Target:  <1 h end-to-end, 7×24 available, in the existing Feishu entry
Proof:   median time-to-answer over 4 weeks, from chat logs
Slice:   one course, text answers only, 3 sales users, 2-week pilot
```

**为什么好：** 每条都可测；闭环是一条真实链路而非演示堆叠；"绝不自动承诺"（价格/退款）按设计留给真人分支。

### 好的范围合同（节选）

```
结果：围栏内订单类型处理时长 38 分钟 → 10 分钟以内
基线：每月 1,200 单，取自 2026-06 工单导出，Owner：运营李经理
本期不做：自动改排程、给供应商发消息、财务类订单
围栏动作：禁止回写 ERP、禁止采购动作、禁止对客户承诺（仅人工）
停止条件：Golden Set 连续两轮评测错误率 >5% → 暂停
业务 Owner：王（运营）；技术 Owner：赵（IT）；风险接受人：运营总监
```

**为什么好：** 排除项与围栏动作明确、停止条件可量化、每项责任都有具名人，下一模块可以在清晰围栏内做设计。

### 好的边界

> "要做：飞书中的课程事实问答。暂不做：图片回复、营销知识库。绝不自动承诺：价格、退款、权益、授权。"

**为什么好：** 三类边界清晰，日后范围膨胀是对书面合同的谈判，而非意外。

</correct_patterns>

<common_mistakes>

### 错误：模糊结果

```text
Target: "让销售更高效"
```

**为什么坏：** 不可测，故不可验收，故不可立项。换成基线→目标增量与一个证据来源。

### 错误：没有非目标

> "范围：建知识库。"

**为什么坏：** 没有"暂不做"与"绝不自动承诺"，项目会把每个相邻功能都吸进来，最终自动回答一个它本不该做的商业承诺。

### 错误：演示形态的"MVP"

> "MVP：交付知识库 + 报表 + 图片回复 + 多课程支持。"

**为什么坏：** 那是一堆互不连接的横向演示。真正的 MVP 是一条纵向链路：一个用户、一个入口、一份数据、一个结果。

### 错误：范围没有排除项与停止条件

```
"一期覆盖订单处理，边缘情况以后再说。"
```

**为什么坏：** 不写"不做什么"的范围会无限膨胀；没有停止条件的阶段无法凭证据终止。必须列出不做清单与数值化停止阈值。

### 错误：没有业务 Owner

```
"IT 牵头，业务那边知道这事。"
```

**为什么坏：** "知道"不是担责。没有接受残余风险、并推动团队改变工作方式的业务 Owner，系统上线后没人用。

### 应拒绝的合理化借口

- **"范围先铺大一点，客户更能感到价值。"**
  → 现实：范围过大正是 AI 项目的死因。完整的最小闭环胜过宽而破碎的覆盖面；围栏守住后再扩。
- **"客户是大机构，给系统放开自动执行没事。"**
  → 现实：模型的"合理回答"不是授权。"绝不自动承诺"与"围栏动作"按设计留给真人，无授权门的自动动作就是一次商业事故。

</common_mistakes>

## 高频错误 <!--a:top-->

1. 结果写成感觉（"更高效"）而非基线→目标
2. "MVP" = 几个演示且无闭环
3. 无"绝不自动承诺"边界、无围栏动作 → 系统做出商业承诺或危险写回
4. 验收由开发者而非业务用户说了算
5. 没有具名业务 Owner / 风险接受人
6. 把 ROI 当已实现收益而非假设
7. 未做三维机会评估就签合同
8. 门禁决策未记录就进入设计

## 交付前检查 <!--a:checklist-->

- [ ] 机会已按价值×可行性×责任打分并记录决策
- [ ] 点名了一个第一用户 + 一个现有入口
- [ ] 结果是可测的基线→目标，且有证据来源
- [ ] 三条边界已写（做 / 暂不做 / 绝不自动承诺）+ 围栏动作已列
- [ ] 每个任务最终负责者无歧义；业务 Owner 与风险接受人已具名
- [ ] 验收口径由业务用户掌握
- [ ] 停止 + 收窄 + 回退条件已定义（数值化）
- [ ] 切出一条真实端到端闭环（非演示堆叠）
- [ ] ROI 按假设定价（收益 vs 完整成本）
- [ ] 范围合同已冻结并签字，开放假设已列
