# 业务发现——找对问题

**目标：** 把一句模糊诉求（"我们要一个知识库/对账机器人"）变成一个有量化基线、有证据支撑的业务问题，并给出"是否真的需要 AI"的判断。交付*问题*，而非*解决方案*。

> **客户的要求不是问题本身。** 客户点名的系统或功能，通常只是他为某个尚未说清的问题给出的"候选解法"。你的工作是找到那个问题。业务发现的产出是下一模块 `02-scoping.md` 的输入。

## 输入与输出

| | |
|---|---|
| 输入 | 客户原始诉求、行业画像（`industry/`）、可访谈名单（业务 Owner、一线操作者、IT/数据 Owner…） |
| 输出 | `DSC-<client>-<YYYYMMDD>-NN` 发现访谈纪要；`STM-<client>-NN` 利益相关者地图；一句话问题陈述 + 量化基线 + 可证伪假设 |
| 下游 | `02-scoping.md`——把问题变成范围合同 |

## 第 1 步：记录原始诉求 <!--a:step1-->

在改写之前，逐字记录客户原话。原文措辞是关于"他们认为哪里错了"的第一条线索。

```text
Raw ask (verbatim): ...         原始诉求（逐字）: ...
Who said it:        <name, role> 谁说: <姓名、角色>
Where it surfaced:  <meeting / ticket / "we've been meaning to...">
Presumed solution:  <the feature they think they want>
```

先不改写。先不承诺任何功能名。

## 第 2 步：画利益相关者地图，找到真正被卡住的人 <!--a:step2-->

先画利益相关者地图（`templates/stakeholder-map.md`），再按地图访谈。每次访谈**批量问 3–5 个问题**；要访谈真正干活的人，而不只是买单的管理者。

| 角色 | 你要从他这里得到什么 |
|---|---|
| 业务 Owner | 谁对结果和风险负责；"成功"值多少 |
| 一线操作者 | 真实工作流、绕行办法、等待与返工 |
| 决策人/预算方 | 优先级，什么情况会杀掉项目 |
| IT/数据 Owner | 系统、权限、数据质量、变更窗口 |
| 受影响方 | 谁会被替代、被审核、被升级求助 |

对每个声称的痛点追问"谁在受苦、多频繁、什么都不改会怎样"，直到能点名**一个人**和**一个痛点时刻**：

| 问题 | 为什么重要 |
|---|---|
| 今天谁在做这件事？ | 真实用户，而非预算负责人 |
| 何时疼？ | 反复出现的时刻，而非日历槽位 |
| 他们退而求其次做什么？ | 绕行揭露出真实成本 |
| 错了会破坏什么？ | 错误后果 → 是否允许用 AI |

每次访谈记录：当前流程、带**频次与成本**的痛点、以前失败的修复尝试、以及他们以为"大家都知道"的隐性约束。产出 `STM-<client>-NN`。

## 第 3 步：还原现状流程（As-Is） <!--a:step3-->

先记录**今天**工作是怎么完成的，再画任何未来功能。瓶颈在*交接或等待*处，而非最后一步。

```
触发 → 步骤 → 交接 → 等待 → 步骤 → 异常路径 → 升级 → 结果

每一步记录：
  Owner:       角色（尽量到具名人）
  System:      工作实际发生在哪个系统
  Time:        典型耗时与 P95 耗时
  Defect:      错误/返工/退回率
  Wait:        排队与审批延迟
  Workaround:  表格、消息催办、私人小本本（上线路径外的真相）
```

## 第 4 步：用多源证据交叉验证 <!--a:step4-->

一次顺畅的访谈是**线索**，不是事实。用记录、数据与观察相互印证。

| 来源 | 能证明什么 |
|---|---|
| 口述流程 | 人们*说*发生了什么 |
| 系统日志/记录 | 实际发生了什么（频率、体量） |
| 业务数据 | 规模、错误、不一致 |
| 现场观察 | 没人提到的等待、绕行、异常 |

只有 **2+ 独立来源**支撑的主张才能升级为"已证实事实"。

## 第 5 步：量化业务基线 <!--a:step5-->

记录改造*前*的状态，项目日后才能证明它变了。基线是测量，不是叙事。**没有基线就不得主张价值。**

| 维度 | 基线测度 | 示例 |
|---|---|---|
| 业务量 | 规模/频率 | 每月 1,200 单异常订单 |
| 时间 | 周期/等待 | 平均处理 38 分钟；P95 为 4 小时；"复杂问题 2–4 小时" |
| 成本 | 人工/返工工时 | 4.5 个人力做人工匹配；"每次升级消耗教研 3 小时" |
| 质量 | 错误/返工率 | 11% 退回/返工率；"8 个回答里 1 个错或过时" |
| 风险 | 暴露面/事故率 | 每季度 3 起合规险情；错答引发退款纠纷 |
| 行为 | 采用/吞吐 | 销售宁可等待而非作答 |

每条数字附**来源**（"前"可核对，"后"才可核对）。若某指标当前无法度量，标注它，并定义 Pilot 期间如何埋点采集（见 `05-pilot-adoption.md`）。

## 第 6 步：区分业务问题、技术症状、方案假设 <!--a:step6-->

绝不能把三件不同的事压缩成一句话：

| 层次 | 定义 | 示例 |
|---|---|---|
| **业务问题** | 当前流程损失了什么价值 | 业务人员等资料、答复不一致 |
| **技术症状** | 工具/系统上可观察的异常 | 检索召回不稳、答复没绑定来源 |
| **方案假设** | 一个仍可被证伪的改动设想 | 受控检索+来源绑定答复或可缩短等待 |

方案假设**不是**已达成的事实；它正是 `04-evaluation.md` 要检验的对象。

## 第 7 步：写成问题陈述 <!--a:step7-->

一句话，逼成固定句式。套不进去，就说明还没找到问题。

```text
<Who> in <what scenario> suffers <what observable loss>
because <what underlying cause>, today costing <baseline number>.
（谁）在（什么场景）因为（什么根因）遭受（什么可观察损失），今天付出（基线数字）。
```

## 第 8 步：判断是否该用 AI <!--a:step8-->

好的 FDE 先证明该做什么，再证明需要 Agent。

| 如果工作是… | 那么用… |
|---|---|
| 确定、可枚举的规则 | 规则 / 传统软件 |
| 基于历史数据的预测 | 预测模型 |
| 围绕文档的检索 | RAG（先于 Agent） |
| 多步推理 + 工具 + 状态 | Agent 工作流 |
| 高风险、高歧义、低频 | 留人工，加辅助 |

若规则或 RAG 已够，硬上 Agent 是范围蔓延，不是进展。

## 模板 / 工件 <!--a:template-->

- `templates/discovery-interview-guide.md` —— 访谈批次问题与访谈纪要骨架
- `templates/stakeholder-map.md` —— 利益相关者地图
- 产出 ID：`DSC-<client>-<YYYYMMDD>-NN`（发现访谈纪要）、`STM-<client>-NN`（相关者地图）

**门禁提示：** 问题可证伪、基线可度量、关键主张 2+ 来源——才可进入 `02-scoping.md`。若多次访谈后问题仍不成立或价值过小，直接**停止**并记录理由（比造一个没人要的系统省更多钱）。

<correct_patterns>

### 好的业务问题陈述（制造/物流）

> "异常订单处理占用 4.5 个人力，平均耗时 38 分钟、退回率 11%，因为分诊人员要人工查 6 个系统且答复不绑定来源。假设：来源绑定的辅助分诊可把耗时降到 10 分钟以内——这正是 PoC 要证伪的对象。"

**为什么好：** 点名工作流、量化基线、把问题与假设分开，并写明什么情况算假设被推翻。

### 好的业务问题陈述（销售/课程）

> "销售在售前咨询中因每个技术问题要等教研 2–4 小时而错失成交窗口，每月估算损失 N 笔降级/流失转化。"

**为什么好：** 点名了谁、场景、可观察损失、原因与基线数字。它不提"知识库"——那是解决方案，留给 `02-scoping.md`。

### 好的基线

| 维度 | 改造前 | 来源 |
|---|---|---|
| 时间 | 复杂问题 2–4 小时 | 销售访谈 + 聊天记录 |
| 质量 | 约 8 个回答中 1 个过时 | 教研抽查 30 例 |

**为什么好：** 每个数字有来源；"前"可核对，"后"才可核对。

</correct_patterns>

<common_mistakes>

### 错误：把功能要求当成问题

```
"客户想要一个问答 Agent，那就做一个问答 Agent。"
```

**为什么坏：** 记录的是客户设想的方案，不是问题。没有工作流、没有基线、没有可证伪假设；采用失败时无人能解释原因。业务发现还没开始就结束了。

### 错误：单一来源当成事实

> "我们跟销售负责人确认过流程了。"

**为什么坏：** 一次访谈是线索。自信的回忆不是证据；系统日志与观察到的实际工作和记忆并不一致。

### 错误：没有基线

> "现在挺慢的，改没改好一看就知道。"

**为什么坏：** 没有数字，就无法定价价值、无法证明变化。"更快"不可测量，交付永远无法验收。

### 应拒绝的合理化借口

- **"客户已经说清要什么了，再访谈只会拖慢进度。"**
  → 现实：提需求的人通常不是干活的人。和一线聊一轮，常常推翻原始需求；发现是最便宜的保险。
- **"基线现在量不了，上线后再估算。"**
  → 现实：没有事前数字就无法证明价值、讲续费故事、发现回退。最迟在 Pilot 埋点。

</common_mistakes>

## 高频错误 <!--a:top-->

1. 把客户点名的功能（"知识库""问答机器人"）当成问题本身
2. 只问一个人就当成了事实（单源可证实）
3. 没有度量的业务基线（"一看就知道"）
4. 业务问题/技术症状/方案假设混成一句话
5. 检查规则/RAG 之前默认"上个 Agent"
6. 描述理想流程而非现状流程

## 交付前检查 <!--a:checklist-->

- [ ] 原始诉求逐字记录，未改写
- [ ] 利益相关者地图完成；点名了真实用户与反复出现的痛点时刻
- [ ] 现状流程已还原，逐步记录 Owner、耗时、缺陷与等待
- [ ] 每项关键主张由 2+ 来源支撑
- [ ] 基线已量化，每个数字有来源（或已写明 Pilot 埋点方案）
- [ ] 问题/症状/假设已写成三条独立陈述
- [ ] 问题陈述符合一句话句式
- [ ] 已记录「是否用 AI」决策与路由理由
- [ ] 门禁决策（继续 / 修订 / 收窄 / 停止）已记录理由
