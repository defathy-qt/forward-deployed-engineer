# 受控试点与组织采用

**目标：** 把通过评测的 PoC 推进到紧密围栏内的真实用户；放权速度只跟随证据；最终交付一个有人运维、有人负责、有人真正使用的系统。**上线是技术事件，采用才是交付。**

> 能跑但没人用的系统，可靠再高也是失败交付。试点要有边界、放权要有证据、上线要有门禁、采用要有设计、交接要有书面责任。

## 输入与输出

| | |
|---|---|
| 输入 | `EVAL-<client>-vN` 评测报告（残余风险）、`SCP-<client>-vN` 范围合同、`arch-<client-slug>-<YYYYMMDD>.md` 架构与 `ADR-*` |
| 输出 | `PLT-<client>-vN` Pilot 计划、`UAT-<client>-vN` 验收记录、`PM-<client>-vN` 采用指标快照、交接记录（含 Land & Expand 种子） |
| 下游 | `06-deployment-runbook.md`（生产部署）、`09-retro-assets.md`（复盘与资产回传）、`08-product-feedback.md`（系统性缺口反馈） |

## 第 1 步：设计 Pilot 围栏 <!--a:step1-->

Pilot 不是放大版 Demo——它是真实用户做真实工作。围栏要在**有限用户、有限场景、有限数据、有限动作、有限时间、成功证据**六个轴上明确决定（FDE-02 六边界），并叠加熔断与每日复盘（FDE-01 四轴）：

```markdown
# Pilot 计划：<客户> — <结果> v<N>   （模板：`templates/pilot-plan.md`）
- 有限用户：  <具名队列，如一个班次 6 名操作员；明确排除谁>
- 有限场景：  <哪些任务在内/在外；商业承诺类业务显式排除>
- 有限数据：  <哪些渠道/来源/时间窗；什么数据绝不进入>
- 有限动作：  <仅建议 / 人工确认；列出围栏内允许的回写>
- 有限时间：  <起止、评审检查点、决策前最长周期>
- 成功指标：  <业务+安全指标，阈值继承自评测；同时写明"什么证据允许扩围">
- 熔断开关：  <谁一键拉下；拉下后回退到什么>
- 每日复盘：  <早上看什么：接管记录、不安全动作、拒绝案例、SLO>
```

评测报告（`04-evaluation.md`）里的每条残余风险都要映射为一条围栏约束或每日复盘项——未证明缺口必须补齐，不能挥手放行。

## 第 2 步：按角色培训 <!--a:step2-->

同一系统，不同人，"如何信任它"不同。培训脚本按角色各一，动手练，不放 PPT：

| 角色 | 必须学会什么 |
|---|---|
| 管理者 | 指标、风险、放权决策（何时该升级/收窄/停止） |
| 领域专家 | 评审、纠错、承担专业风险 |
| 一线用户 | 入口、适用任务、看依据/引用、何时转人工 |
| 运维 | 监控、故障处理、回滚路径 |

没学会如何接管的用户，要么盲信要么盲拒——两者都摧毁价值账。

## 第 3 步：搭起反馈闭环 <!--a:step3-->

每个生产失误都变成一个带标签的样本，路由到正确负责人——知识还是系统——而非一次无声的恼火：

```text
Feedback entry: <在既有入口内，一键>
Failure labels: <依据错 / 结论错 / 上下文错 / 动作不安全 / 需要多模态 / ...>
Routing:        <知识缺口 → 知识 Owner；系统性缺陷 → 工程>
响应 SLA:        <谁在多久内处理并回写一条修复样本>
```

反馈路由与结构细节见 `08-product-feedback.md`；修复后样本永久鉴权入库（`07-client-debug.md`）并触发 Golden Set 回归（`04-evaluation.md`）。

## 第 4 步：放权等级匹配证据 <!--a:step4-->

放权逐级授予，**每次晋级都需要更强证据、更紧人工控制、更稳运行保障和具名责任人**。放权跟随证据，不跟随热情：

| 等级 | 系统可以…… | 晋级前所需证据 |
|---|---|---|
| **L0 影子运行** | 只观察；人做全部工作，系统记录"本会怎么做" | 评测通过条件达成；Golden Set 已冻结 |
| **L1 辅助决策** | 给建议；人决定并执行每个动作 | 观察窗内建议精准率达标；不安全建议 = 0 |
| **L2 有限自动化** | 执行围栏内低风险动作；其余仍人工确认 | UAT 通过；SLO+告警在线；回滚演练过；Owner 书面签字 |
| **L3 全自动（围栏内）** | 围栏范围内无需逐动作确认运行 | L2 稳定运行约定期限；故障注入通过；审计验证；风险接受人具名 |

无论处于哪一级，**高风险 / 低置信 / 边界用例都转人工**——模型的"合理回答"不是授权。L3 绝不静默越出围栏：扩大范围 = 新范围从 L1 重新走。

## 第 5 步：执行业务 UAT <!--a:step5-->

UAT 由**业务用户用自己的真实任务**完成，不是 FDE 自己点一遍顺利路径（模板：`templates/uat-checklist.md`，按 `02-scoping.md` 约定的验收口径执行）：

- 脚本化任务覆盖正常、异常、拒绝/升级路径。
- 用户必须看得到依据/引用，并知道如何接管。
- 逐任务记录通过/失败、耗时、置信度，以及每一句口头异议。
- UAT 结论由业务 Owner 书面签字，列明已知限制。

```text
User task: <真实目标>
Steps:     <用户实际会做的操作>
Expected:  <正确结果长什么样>
Sign-off:  <具名 Owner，日期>
```

## 第 6 步：Production 上线门禁 <!--a:step6-->

以下每项都是**证据而非声明**；缺一项即阻断上线:

| 门禁项 | 所需证据 |
|---|---|
| 评测 | 冻结 Golden Set 达通过阈值；回归干净 |
| 围栏 | 范围/动作限制已在配置中强制生效 |
| 放权 | 批准等级与第 4 步证据匹配并签字 |
| 可观测 | 指标/日志/Trace/审计在线；告警已证实能触发 |
| 可靠性 | 五类故障注入通过（见 `06-deployment-runbook.md`）；降级路径已知 |
| 回滚 | 手册回滚已演练；覆盖迁移与 flag |
| 安全 | 权限、审计留存、数据边界检查已签字 |
| 责任 | 业务与技术 Owner、值班人书面具名 |

## 第 7 步：度量采用、推动采用 <!--a:step7-->

**先量行为，再谈价值。** 采用描述的是行为，不是登录数：

| 指标 | 回答什么 |
|---|---|
| 使用率 | 他们真的用了吗？ |
| 任务完成率 | 它完成预定工作了吗？ |
| 直接采纳率 | 结果未经修改就被接受了吗？ |
| 人工干预率 | 还有多少需要人介入？ |

有意识地推动采用，没人用的系统是货架摆设：

| 采用杠杆 | 具体动作 |
|---|---|
| 角色化培训 | 见第 2 步；发布时再跑一轮 |
| 嵌入工作流 | 系统在既有工具内打开，不另记一个网站 |
| 嵌入激励 | 使用率/接管质量进入团队 KPI；"用不用都行"必然失败 |
| 反馈渠道 | 一个明显的"答复有误"入口；响应有 SLA（见第 3 步） |
| 种子用户 | 每班/每组指定种子用户带教同伴 |
| 使用度量 | 每周跟踪四指标与业务指标，产出快照 `PM-<client>-vN` |

## 第 8 步：交接与 Land & Expand <!--a:step8-->

FDE 撤出前完成正式交接（收尾邮件不转移责任）：

1. **知识交接：** 手册、ADR、已知限制、升级树。
2. **运维交接：** 值班轮转、看板、告警归属、凭证（写入 `06-deployment-runbook.md` 的 runbook）。
3. **责任交接：** 业务 Owner（内容与结果）+ 技术/系统 Owner（运行与值班）+ 升级路径（按顺序找谁）书面验收。
4. **扩展种子：** 记录下两个候选工作流及其基线数字——围栏内的使用数据就是扩展证据。
5. **资产回传：** 可复用部分进入 `09-retro-assets.md`；系统性缺口进入 `08-product-feedback.md`。

## 第 9 步：Pilot 结束的四出口决策 <!--a:gate-->

Pilot 窗口结束或任一停止条件触发时，用与评测一致的四出口词汇做决定并记录证据（见 `04-evaluation.md` 第 7 步）：

| 出口 | 条件 | 下一步 |
|---|---|---|
| **继续** | 门禁全过、采用指标达标、残余风险可接受 | 扩展到更大围栏/下一轮；L3 仅随证据授予 |
| **收窄** | 价值成立但仅在小范围/低风险围栏成立 | 缩小角色/场景/动作后继续跑 |
| **修订** | 方向成立，某层证据不过 | 回到 04/05 对应层修复后重测 |
| **停止** | 采用不成立或价值被证伪 | 记录证据，交 09 复盘，不强行续跑 |

```markdown
# 四出口决策记录：<客户> — <Pilot 名称> <日期>
- 出口：<继续 / 收窄 / 修订 / 停止>
- 依据：<门禁证据、四指标、残余风险清单、未恢复的熔断次数>
- 风险接受人：<具名>
- 下一步动作与 Owner：<谁在何时做什么>
```

## 模板 / 工件 <!--a:template-->

- `templates/pilot-plan.md` —— Pilot 围栏计划（用户/场景/数据/动作/时间/成功）
- `templates/uat-checklist.md` —— 业务 UAT 检查与签字
- `templates/adoption-plan.md` —— 采用计划（培训/嵌入/激励/种子/度量）
- 产出 ID：`PLT-<client>-vN`、`UAT-<client>-vN`、`PM-<client>-vN`

**门禁提示：** 无围栏、无熔断、无每日复盘、无业务签字 UAT、无八项门禁证据 → 不得进入 `06-deployment-runbook.md`。上线不是项目结束，采用才是。

### 好的 Pilot 围栏

```
用户：  夜班分诊组（6 人），组长不纳入自动路径
场景：  仅订单异常分诊；价格/承诺/财务排除
数据：  仅国内订单、订单类型 R-01..R-04、近 90 天
动作：  仅建议；禁止回写 ERP；升级草稿需人工一键发送
周期：  2026-07-21 → 2026-08-04，每 2 天评审，08-04 硬停止
成功：  无纠正率 ≥95%，不安全建议 = 0，处理时长 ≤10 分钟 → 允许扩到下一班
熔断：  值班翻 flag pilot_enabled=false；1 分钟内回退人工
每日：  09:30 站会前读接管日志、拒绝案例、SLO 看板
```

**为什么好：** 每个轴都有具名与数字；成功指标写明"什么证据允许扩围"；熔断是一个动作；每日复盘点名具体材料；排除项与纳入项同样明确。

### 好的放权决策

> "仅对订单类型 R-01/R-02 把分诊建议从 L1 升到 L2：影子运行 10 天精准率 97.4%、不安全建议为 0；UAT 于 08-01 签字；07-31 演练确认 SLO 告警触发；08-02 演练回滚；运营总监书面接受残余风险。R-03/R-04 维持 L1。"

**为什么好：** 按案例类型分别晋级，逐条引用带日期的证据，证据较弱的范围留在低等级而非一刀切晋级。

### 好的试点六边界（FDE-02 视角）

```text
Users:    3 named sales reps
Scenarios:course-fact questions only; commercial promises excluded
Data:     one course corpus
Actions:  read-and-answer only; no write-back, no external send
Cycle:    2 weeks; success = median time-to-answer < 1h AND ≥ 1 real use/day
```

**为什么好：** 每个边界都是一次决定；"不写回 / 不做商业承诺"在系统赢取信任前保护业务。

### 好的采用快照

> "第 2 周：3/3 销售每天使用；80% 回答未经修改直接采纳；2 次升级都是商业承诺类（正确交给真人）。绿灯：扩到 10 人。"

**为什么好：** 行为指标，而非登录数；升级记录恰好证明边界在正确方向起作用。

<common_mistakes>

### 错误：Pilot 当大 Demo

```
"先给所有人跑两周看看效果。"
```

**为什么坏：** 无围栏、无熔断、无每日复盘——失败时是在真实客户面前满负荷爆炸，且没有可供学习的证据链。使用习惯、知识错误、权限 bug、系统故障同时被放大。

### 错误：直接全员上线

```text
Pilot: "把整个团队都铺开看看。"
```

**为什么坏：** 全员铺开让失败来源无法隔离。有边界的试点才能分辨"是知识错、权限 bug 还是系统故障"。

### 错误：放权快于证据

```
"UAT 看着很好，直接让它回写 ERP 吧。"
```

**为什么坏：** 跳过 L0/L1/L2 证据、回滚演练和书面风险接受。一次错误回写摧毁的信任，比一个月正确建议建立的还多。放权跟随证据，不跟随热情。

### 错误：高风险无人工复核

> "Agent 自动决定并执行退款，更快。"

**为什么坏：** 模型的"合理回答"不是授权。高风险动作需要人工复核与审计链（见 `03-integration-architecture.md`），否则一次错误就是一次商业事故。无论哪级，高风险都转人工。

### 错误：把上线当项目结束

```
"周五部署，周一 FDE 撤场。"
```

**为什么坏：** 没有培训、工作流嵌入、激励、种子用户和每周使用复盘，系统会悄悄变成货架摆设。采用工作从上线才开始。

### 错误："被采用" = "入口存在"

> "入口上线了，大家有权限了，所以算被采用。"

**为什么坏：** 存在的入口不等于被用的入口。先量使用、完成、采纳、干预，再谈采用。

### 应拒绝的合理化借口

- **"Pilot 用户最终总会覆盖所有人，没必要设围栏。"**
  → 现实：无围栏的 Pilot 会把每个未知失败变成生产事故。围栏正是让你快速学习而不烧信任的装置。
- **"用户自己会摸索，正式培训是多余开销。"**
  → 现实：没学会如何接管的用户会盲信或盲拒——培训是交付物的一部分。
- **"交接就是发一封收尾邮件。"**
  → 现实：收尾邮件不转移责任。双 Owner 书面验收、在线值班路径、演练过的运维，才叫交接。上线后无人认领知识/系统 Owner，采用就立不住。
- **"Pilot 没人用是因为大家忙，再等等。"**
  → 现实：采用不是等来的，是设计出来的——嵌入工作流、嵌入激励、种子用户，缺一不可。

</common_mistakes>

## 高频错误 <!--a:top-->

1. Pilot 没有围栏/没有一键熔断/没有每日复盘（或试点 = "全员铺开看"）
2. 放权晋级快于证据积累；高风险动作无人工复核
3. UAT 由 FDE 而非业务用户执行
4. 上线门禁靠声明而非证据
5. 反馈无人负责 → 失误变成噪音
6. 用"有权限/入口存在"而非"被使用/被采纳"衡量采用
7. 无角色化培训、无采用计划
8. 未完成书面责任交接 FDE 就撤场（无长期负责人）
9. 无带基线的扩展种子；无资产/反馈回传

## 交付前检查 <!--a:checklist-->

- [ ] Pilot 围栏六轴明确（用户/场景/数据/动作/时间/成功），有熔断与每日复盘
- [ ] 每条评测残余风险已映射为围栏约束或复盘项
- [ ] 角色化培训已交付（管理者/专家/一线/运维）
- [ ] 反馈闭环带标签与路由已就位，有响应 SLA
- [ ] 放权等级与已积累证据匹配；扩范围则等级重置；高风险/低置信/边界转人工
- [ ] UAT 由业务用户覆盖正常/异常/拒绝路径并书面签字
- [ ] 八项上线门禁均有证据
- [ ] 四项采用指标已定义、测基线并每周产出快照
- [ ] 交接覆盖知识、运维与书面责任验收；知识/系统/升级负责人具名
- [ ] 已记录扩展种子基线与资产/反馈回传；四出口决策已附证据记录
