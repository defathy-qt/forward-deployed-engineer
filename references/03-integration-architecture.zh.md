# 集成架构

**目标：** 一份具体可实施的设计，而非演示稿。每个集成点写明协议、认证、数据形态、失败模式；每个影响评测或运维的设计选择都落成一张 ADR；设计落在一个**稳定的业务模型**上，让 Agent 面向真实对象工作，而非裸读原始表。

> 本模块把 `02-scoping.md` 的闭环变成可建设计划，并输入 `04-evaluation.md` 与 `06-deployment-runbook.md`。

## 输入与输出

| | |
|---|---|
| 输入 | `SCP-<client>-vN` 范围合同、发现基线、客户系统与组织信息 |
| 输出 | `arch-<client-slug>-<YYYYMMDD>.md` 集成架构文档；`ADR-NNNN-<slug>.md`；连接器清单（含可复用性评分） |
| 下游 | `04-evaluation.md`（PoC 纵向切片）、`06-deployment-runbook.md`（部署输入） |

## 第 1 步：同时盘点系统与组织 <!--a:step1-->

对每个相关系统记录：

| 字段 | 示例 |
|---|---|
| 系统名与版本 | "Legacy ERP 2019"、"Internal CRM v4"、"On-prem data warehouse" |
| 部署形态 | 本地 / 私有云 / SaaS / 隔离网络 |
| 持有数据 | 主数据、交易日志、参考数据 |
| 集成接口 | REST、SOAP、SFTP、ODBC、Kafka、纯文件 |
| 认证与网络约束 | 仅 VPN、mTLS、本地 IdP 的 OAuth2、无外网 |
| 数据量与频率 | 每日 50 万行、实时 vs 夜间批 |
| 数据质量与 Owner | 完整度、新鲜度、谁修脏数据、SLA |
| 客户联系人 | 姓名、团队、升级路径 |

只盘系统不够——FDE 还要把**组织**继承进来——找不到审批人、没记录的线下绕行，是 Pilot 延期最常见的原因：

| 组织事实 | 为什么重要 |
|---|---|
| 变更决策链 | 开连接器、开防火墙端口、开账号分别谁批 |
| 真实流程 vs 纸面流程 | 工作在哪里离开系统（Excel、群消息、私人记录） |
| 运维归属与值班 | 上线后谁运维、凌晨 3 点谁接警 |
| 变更/冻结窗口 | 月末、审计、封网期等会阻断部署的时段 |
| 采购与安全评审周期 | 白名单、license、渗透测试实际要多久 |

## 第 2 步：定义数据流 <!--a:step2-->

每条流写明：

```
[源] → [抽取] → [传输] → [转换] → [落地]

Protocol:  REST / SFTP / JDBC / Kafka / file-watch
Auth:      OAuth2 client-credentials / username+key / 等
Schema:    输入列/类型、输出列/类型、校验规则
Cadence:   实时 / 每小时批 / EOD 文件投递
Error:     失败时——重试、DLQ、告警、人工工单
```

## 第 3 步：设计集成层与防腐层 <!--a:step3-->

三件工件：

1. **网络与认证图**——组件、谁跟谁通信、开放端口、逐跳认证。
2. **连接器清单**——每个连接器一行：类型（MCP server / 定制脚本 / 反向 SSH 隧道 / SFTP watcher）、语言、工作量（S/M/L）、可复用性（一次性 / 可参数化 / 可产品化——诚实打分）。
3. **配置面**——客户管理员部署后需配置的内容（环境变量、密钥、feature flag、白名单）。

每个外部系统外都应放一层**防腐层**：把它的协议与词汇适配为稳定内部接口，让供应商更换不会波及 Agent 与工作流。

标注哪些连接器属于 PoC 所需的**最小端到端链路**——链路假设未被证明前，不要先把整张集成图建完。

## 第 4 步：为业务世界建模（轻量本体层） <!--a:step4-->

别让 Agent 猜数据库字段。定义一套稳定的业务模型——对象、关系、动作、规则、权限——再把每个外部字段映射到它上面。

| 元素 | 问题 | 示例（订单履约制造） |
|---|---|---|
| 对象 | 存在哪些实体？ | 订单、工厂、产线、物料、库存、客户、负责人 |
| 关系 | 它们如何连接？ | 订单→物料→产线；批次→库存位置 |
| 动作 | 谁可以做什么？ | 提议调拨、调整排产、通知工厂 |
| 规则 | 哪些确定性约束适用？ | 替代料必须通过 QA；超上限→升级 |
| 权限 | 谁能查看/执行/写回？ | 计划员提议；负责人批准；系统账户写 ERP |

本体层组织业务世界，但不替代规则、工作流、Agent、人或源系统——它把它们连起来。

## 第 5 步：加固身份、权限与审计 <!--a:step5-->

"能调用工具"不等于"有权执行动作"。每个高风险动作都必须知道是谁、为什么、且可追溯。

| 层 | 问题 | 防护 |
|---|---|---|
| 身份 | 谁/什么在调用（用户还是服务）？ | SSO、服务账户、租户隔离 |
| 授权 | 该身份能做什么？ | 最小权限、RBAC/ABAC、工具白名单 |
| 人工授权门 | 哪些动作需要人？ | 状态变更类工具走审批/双人复核 |
| 审计 | 如何可追溯且不可抵赖？ | 防篡改日志：谁→身份→依据→工具+参数→状态→结果 |

需显式缓解的威胁：直接/间接提示注入、工具越权、数据外泄、检索内容投毒。只读工具保持只读；状态变更工具一律走授权门。

## 第 6 步：记录架构决策（ADR） <!--a:step6-->

任何回退成本高、或影响评测/安全/运维的选择，实施前都写一页 ADR：

```markdown
# ADR-NNNN：<决策标题>
- 状态：proposed | accepted | superseded by ADR-xxxx
- 背景：<迫使选择的约束，附证据>
- 候选方案：<方案 A / B / C，各一行权衡>
- 决策：<选什么>
- 后果：<什么变容易、什么被锁死、什么不能再做>
- 验证链接：<哪次 PoC/评测结果或测试确认它>
```

## 第 7 步：风险登记 <!--a:step7-->

| 风险 | 缓解 |
|---|---|
| 客户 schema 无预告变更 | 锁版本 + 漂移告警 |
| 本地系统计划停机 | 优雅降级；排队重放 |
| 安全审查阻断部署 | 提前备问卷与评审文档 |
| 隔离网络中继延迟 | 尽早压测；书面约定 SLA |
| 本体模型在真实数据下错误 | 全面铺开前用 2+ 真实案例校验 |
| 组织变更找不到审批人 | 具名审批人+备份，提前锁定周期 |

## 第 8 步：产出文档 <!--a:step8-->

```markdown
# 集成架构：<客户> — <日期>

## 1. 摘要（3 句话）
## 2. 客户系统与组织清单
## 3. 数据流图（ascii 或 mermaid） + 防腐层边界
## 4. 连接器规格（含可复用性评分与 PoC 切片标注）
## 5. 业务本体（对象 / 关系 / 动作 / 规则 / 权限）
## 6. 身份、权限与审计设计
## 7. 认证与网络设计
## 8. 配置面
## 9. ADR 索引
## 10. 风险登记
## 11. 实施分期（PoC 切片 / wave 1 / wave 2 / future）
## 12. 待澄清问题（供客户评审）
```

**不要立即构建**——本模块只产出设计。实现须在客户与内部利益相关方签字后开始，
且第一个构建对象是 PoC 纵向切片。

## 模板 / 工件 <!--a:template-->

- `templates/adr.md` —— 一页 ADR
- 产出 ID：`arch-<client-slug>-<YYYYMMDD>.md`、`ADR-NNNN-<slug>.md`

**门禁提示：** 数据流五要素、组织盘点、本体层、授权审计链、ADR、风险缓解齐全，且 PoC 切片已被标注——才可进入 `04-evaluation.md`。客户端点未盘点前，不为没画过的系统设计连接器。

<correct_patterns>

### 好的数据流规格

```
[WMS (on-prem, Oracle 19c)] → [nightly export job → CSV on SFTP] → [platform SFTP watcher] → [parse + validate] → [inventory_snapshots table]

Protocol:  SFTP (ssh-key auth, port 2222, client-side IP allowlist required)
Auth:      ED25519 keypair; client rotates annually, notifies 7 days ahead
Schema:    18 columns (sku, qty_on_hand, qty_reserved, location_code, ...)
           Validation: sku matches ^[A-Z]{3}\d{6}$; qty_on_hand >= 0
Cadence:   Nightly 02:00 client-local; file lands by 02:30; platform processes by 03:00
Error:     File missing by 03:00 → alert on-call; do NOT re-run client job unilaterally
```

**为什么好：** 每个字段都具体（端口 2222、ED25519、02:00 客户本地时间）；失败模式写明"不可做"（保护客户）；错误路径可执行。

### 好的连接器行

| 字段 | 值 |
|---|---|
| Name | `sftp-inventory-watcher` |
| Type | SFTP watcher（平台原生） |
| Language | 仅配置（无代码） |
| Effort | S（2h） |
| Reusability | 可产品化——可参数化用于任意 SFTP CSV 投递 |

**为什么好：** 可复用性诚实打分（这条确实可产品化），工作量有量化，类型具体到能据此定工作量。

### 好的本体片段

| 元素 | 条目 |
|---|---|
| Object | `order`、`material`、`line`、`stock` |
| Relation | `order requires material`；`batch located_at location` |
| Action | `propose_stock_transfer`（计划员）→ `approve`（负责人） |
| Rule | 替代料必须 `passed_qa == true` |
| Permission | 系统写回仅允许经 `sys-erp` 账户，且留审计 |

**为什么好：** Agent 不再猜原始列，而是在受治理对象上工作；每次变更都有负责人与规则，"确定性结果"在运行中得以存续。

### 好的 ADR

```markdown
# ADR-0007：客户导出用"锁 schema + 漂移告警"解析，不用宽松解析
- 背景：客户 WMS 未通知改列（见 ISS-atlas-20260629-01）
- 候选：A）宽松自适应（脆弱、静默丢数）B）锁 schema + 告警
- 决策：B；严格按锁定的 v2 解析，列数一变即阻断加载并告警
- 后果：新列需协同迁移；但不可能发生静默损坏
- 验证：Golden Set GS-014/GS-027 通过；故障注入 FI-03
```

**为什么好：** 把一个看似可回退的选择显式化，记录权衡与背后证据，并把决策与评测结果挂钩。

</correct_patterns>

<common_mistakes>

### 错误：模糊的数据流

```
"Inventory data will be transferred via SFTP. Auth will be configured by the client.
Errors will be handled appropriately."
```

**为什么坏：** 无协议细节、无认证细节、无失败语义。运维无法执行。

### 错误：占位认证

```
Auth: <TBD with client security team>
```

**为什么坏：** TBD 不是设计。要么给具体默认（如"ED25519 密钥对，客户提供公钥"），要么列 2-3 个选项带权衡。TBD 会随架构文档一起签发，然后变成"已批准的设计"。

### 错误：Agent 裸读原始表

> "让 Agent 直接查 ERP 表——少几跳。"

**为什么坏：** Agent 继承了每个供应商的字段名、编码与不一致，schema 一变就崩。把外部字段映射到稳定业务模型，让 Agent 在防腐层之后操作该模型。

### 应拒绝的合理化借口

- **"认证实现时再说，客户安全团队会告诉我们。"**
  → 现实：认证约束会重塑整个架构。晚到的"无外网"约束会让连接器选型作废。第 1 步就锁定。
- **"客户说 schema 稳定，不需要漂移检测。"**
  → 现实：客户对自己系统的断言是不可信数据。漂移检测是廉价保险；客户"我们从不改"的记忆不是。
- **"组织流程问题不是工程问题，设计里先跳过。"**
  → 现实：找不到审批人、没记录的线下绕行，是 Pilot 延期最常见的原因。组织也是架构的一部分。

</common_mistakes>

## 高频错误 <!--a:top-->

1. 数据流用占位认证（`<TBD>`）
2. 无业务本体——Agent 直接指向原始表
3. 连接器清单可复用性评分不诚实或缺失
4. 风险登记无缓解措施（只有风险）
5. 架构文档写"错误得到适当处理"
6. 缺组织盘点（审批人、真实流程、运维归属、冻结窗口）
7. 状态变更类工具无人工授权门/审计
8. 高成本决策没有 ADR
9. PoC 切片未证明就先建完整集成图
10. 无待澄清问题章节——假设当成事实

## 交付前检查 <!--a:checklist-->

- [ ] 每条数据流五要素齐全（protocol + auth + schema + cadence + error）
- [ ] 每个连接器四字段齐全（type + language + effort + reusability）
- [ ] 组织盘点覆盖审批人、真实流程、运维、冻结窗口
- [ ] 防腐层与业务本体已定义并覆盖对象/关系/动作/规则/权限
- [ ] 身份→授权→人工授权门→审计链已设计；状态变更工具一律走授权门
- [ ] 已标注 PoC 切片连接器，后续分期显式后置
- [ ] 高成本/涉安全的选择已写 ADR 并挂证据
- [ ] 每条风险都有缓解
- [ ] 无 `<TBD>` / `<fill-me>` 未配具体默认值
- [ ] 待澄清问题列出未知项
