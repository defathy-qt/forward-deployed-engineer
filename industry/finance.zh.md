# 行业画像：金融（银行/保险/证券）

> 用法：discovery 阶段对照本画像快速建立行业语境；它是行业约束层，不替代现场调研。
> 金融行业监管解释必须转交给合规/法务专家，FDE 不自行解释监管条文。

## 1. 业务对象与核心流程

| 对象 | 说明 | FDE 常见切入点 |
|---|---|---|
| 客户 | 对私/对公客户、KYC、画像与适当性 | 客户经理辅助、资料核验 |
| 产品/合约 | 存贷、保单、理财、合约条款 | 产品条款问答、材料生成辅助 |
| 交易/流水 | 交易、清算、对账、差错 | 差错分诊、对账异常解释 |
| 风控/合规 | 反洗钱、授信、可疑交易、报送 | 可疑线索辅助研判（不自动定性） |
| 运营/客服 | 工单、知识库、外呼/坐席 | 坐席助手、工单自动分类草稿 |
| 投研/文档 | 研报、公告、制度库 | 依据绑定的检索问答、摘要 |

## 2. 典型系统地形

- 核心系统/总账、信贷、保单核心、交易系统（变更窗口极严、几乎不可直连写）
- CRM/客户中台、影像系统、工单平台、统一知识库
- 数据仓库/数据湖、实时风控引擎；企业服务总线 ESB
- 集成现实：私有云/专区部署为主，强堡垒机、强审计、接口走 ESB/文件交换平台

## 3. 高频 FDE 场景与价值基线

| 场景 | 典型基线（现场重测） | 结果指标 |
|---|---|---|
| 坐席/客户经理助手 | 平均处理时长、话后整理时长 | AHT、话后整理时长、合规话术命中率 |
| 制度/条款问答 | 翻制度库、答复口径不一 | 引用可溯率、无纠正率 |
| 工单智能分诊 | 人工分类与派单 | 分类准确率、派单时长 |
| 差错/对账异常 | 跨系统人工排查 | 定位时长、一次解决率 |

## 4. 合规与安全要点

- 《个人信息保护法》《数据安全法》及金融监管要求：最小必要、分级分类、可审计
- 客户信息严禁出域；测试数据必须脱敏/合成；模型输出可解释、可追溯到人
- 营销/投资建议受适当性约束：建议类动作必须人审，系统只出草稿与依据
- 可解释与留痕是硬门槛：依据层错误（引用不支撑结论）按失败计
- 高可用与灾备：SLO 严格，变更窗口、灰度、回滚要求高于一般行业

## 5. 推荐模块组合

01-discovery（合规与业务双 Owner）→ 03-integration-architecture（ESB/文件交换/
专区拓扑，全部 ADR）→ 04-evaluation（动作层不安全=0 为硬否决；对抗层含诱导越权
与 PII 抽取测试）→ 05-pilot-adoption（L0/L1 停留时间长，L2 仅限低风险围栏）
→ 06-deployment-runbook（审计事件四件套、严格灰度）→ 10-airgap-deploy（专区/信创常见）

## 6. 典型陷阱（现场高频）

1. 用准确率单一指标过关，忽略依据层与动作层；金融场景一条错误建议即事故
2. 用真实客户数据做演示/测试，构成数据违规；一律合成或脱敏
3. 让系统直接给授信/理赔/投资结论，越过适当性与人审
4. 忽略模型输出留痕，事后无法向监管/审计还原"为什么这么答"
5. 低估安全评审与变更窗口周期，项目时间线不预留评审 lead time
6. 把监管口径当常识写进规则；监管解释必须由合规专家确认并版本化
